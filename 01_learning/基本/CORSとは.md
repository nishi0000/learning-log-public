- 扱ったテーマ：CORS の意味、略称、役割、ブラウザ・API Gateway・Lambda の関係、誰が判断するか、なぜその仕組みがあるか、CORS の限界
    

### 1. 扱ったトピック一覧（時系列）

-  トピック：CORS の略称確認
    
    - 何を扱った：CORS という用語の正式名称
        
    - 結論：
        
        - CORS = Cross-Origin Resource Sharing
            
    - 覚えるもの：
        
        - CORS → Cross-Origin Resource Sharing
            
-  トピック：CORS がどういうものか
    
    - 何を扱った：CORS の意味
        
    - 結論：
        
        - 異なるオリジン間でのリソース共有を制御する仕組み
            
        - あるWebページから、別のオリジンのサーバーにアクセスしてよいかをブラウザが判定するための仕組み
            
        - オリジンは主に「スキーム（http / https）」「ホスト名」「ポート番号」の組み合わせ
            
    - 覚えるもの：
        
        - CORS は「異なるオリジン間でのアクセス可否をブラウザが扱う仕組み」
            
        - オリジン = スキーム + ホスト名 + ポート番号
            
-  トピック：誰が判断しているか
    
    - 何を扱った：CORS の判定主体
        
    - 結論：
        
        - 判断しているのはブラウザ
            
        - WebページがAPIにリクエストを送る
            
        - サーバー（Lambdaそのものというより通常はAPI Gatewayなど）がレスポンスを返す
            
        - ブラウザが、そのレスポンスにCORS用の許可ヘッダがあるか見て、JavaScriptに渡してよいか判断する
            
        - 許可情報を出すのはサーバー側、最終的に判断して止めるのはブラウザ
            
    - 覚えるもの：
        
        - 許可情報を返すのはサーバー側
            
        - 判定して止めるのはブラウザ
            
-  トピック：Lambda / API Gateway の文脈での理解
    
    - 何を扱った：Vue から Lambda を呼ぶ流れと、CORS がどこで関係するか
        
    - 結論：
        
        - Vueのページを開く
            
        - ページ内のJavaScriptが API Gateway のURLにGETリクエストを送る
            
        - API Gateway がそのリクエストを受け取る
            
        - API Gateway が Lambda を呼ぶ
            
        - Lambda が処理して、結果を API Gateway に返す
            
        - API Gateway がHTTPレスポンスとしてブラウザに返す
            
        - そのあとブラウザが、その返ってきたレスポンスを見て「このページのJavaScriptに読ませていいか」を確認する
            
        - API Gateway / Lambda は返す、ブラウザがその返事をVueのコードに渡していいか判定する
            
    - 覚えるもの：
        
        - 通信の流れ：Vue → API Gateway → Lambda → API Gateway → ブラウザ
            
        - CORS は最後の「ブラウザがJavaScriptに渡すか」の判定で関係する
            
-  トピック：許可証がないとどうなるか
    
    - 何を扱った：レスポンスに許可情報がない場合の動作
        
    - 結論：
        
        - Lambda / API から返ってきたレスポンスに「このWebページは受け取っていいよ」という情報が入っていないと、ブラウザがJavaScriptからその値を使わせない
            
        - 「受け取らない」より「JavaScriptに読ませない」のほうが近い
            
        - サーバー「返事は返した」
            
        - ブラウザ「でも許可証ないから、画面のJavaScriptには見せない」
            
    - 覚えるもの：
        
        - 許可情報がないと、ブラウザはJavaScriptに読ませない
            
        - 「返ってこない」ではなく「使わせない」に近い
            
-  トピック：なぜそんな仕組みがあるか
    
    - 何を扱った：CORS の目的
        
    - 結論：
        
        - 悪意のあるサイトが、別サイトの情報を勝手に読むのを防ぐため
            
        - そのページを開いているサイトに、他サイトの返事を勝手に読ませないための仕組み
            
        - リクエストを送れるかどうかだけの話ではなく、返ってきた内容を読んでいいかを制御している
            
    - 覚えるもの：
        
        - CORS は「他サイトの返事を勝手に読ませないための仕組み」
            
        - 制御対象は「返ってきた内容を読めるか」
            
-  トピック：怪しいサイトが自分で許可すると言ったらどうなるか
    
    - 何を扱った：誰の許可が有効なのか
        
    - 結論：
        
        - 怪しいサイト自身が「許可するよ」と言っても意味がない
            
        - 許可証を出すのは「アクセスされる側のサーバー」
            
        - 取りに行く側が勝手に許可を名乗ってもダメ
            
        - 取られる側が、この相手なら読んでいいと返したときだけOK
            
    - 覚えるもの：
        
        - 有効なのはアクセスされる側のサーバーの許可
            
        - アクセスする側が勝手に名乗っても無効
            
-  トピック：悪いサイトがAPIをたたいた場合の挙動
    
    - 何を扱った：許可されていないサイトからAPIを呼んだときの動き
        
    - 結論：
        
        - 悪いサイトがAPIをたたく
            
        - APIはレスポンスを返すことがある
            
        - その悪いサイトのオリジンがAPI側で許可されていなければ、ブラウザがそのレスポンスを悪いサイトのJavaScriptに使わせない
            
        - 「値を返さないようにする」より、「返ってきた値をそのページのJavaScriptに読ませないようにする」が正確
            
    - 覚えるもの：
        
        - 許可されていないオリジンには、ブラウザがJavaScriptから読ませない
            
        - 「通信を止める」ではなく「読ませない」が近い
            
-  トピック：CORS の限界
    
    - 何を扱った：ブラウザを改造した場合やネットワーク上ではどう見えるか
        
    - 結論：
        
        - CORSはブラウザに対する制御
            
        - ブラウザを改造したり、CORSチェックをしない別のクライアントを使えば、読めてしまうことがある
            
        - CORSは「絶対にデータを取れなくする仕組み」ではない
            
        - 「普通のブラウザ上のJavaScriptから勝手に読まれにくくする仕組み」
            
        - 値そのものは返ってきていることがある
            
        - ネットワークタブに見えることもある
            
        - 本当に大事なのは、見せてはいけないデータはCORSだけに頼らず、認証・認可で守ること
            
        - CORS はブラウザのJavaScriptに読ませるかの制御
            
        - 認証・認可は、その人にデータを返してよいかの本当の制御
            
    - 覚えるもの：
        
        - CORS はブラウザ向けの制御
            
        - CORS だけで安全にはならない
            
        - 本当の保護は認証・認可で行う
            
-  トピック：このスレッドで固まった最終理解
    
    - 何を扱った：CORS の最終的な理解の整理
        
    - 結論：
        
        - CORS は、異なるオリジン間でのリソース共有を制御する仕組み
            
        - 許可情報を返すのはサーバー側
            
        - その許可情報を見て、JavaScriptに渡してよいかを判断するのはブラウザ
            
        - API Gateway / Lambda が返したレスポンスに許可情報がないと、ブラウザがその内容をJavaScriptに使わせない
            
        - CORS は悪意あるサイトが他サイトの返事を勝手に読むのを防ぐための仕組み
            
        - ただしCORSはブラウザ向けの制御であり、絶対的な防御ではない
            
        - 見せてはいけないデータは認証・認可で守る必要がある
            
    - 覚えるもの：
        
        - CORS = Cross-Origin Resource Sharing
            
        - 判定主体はブラウザ
            
        - 許可情報はサーバー側が返す
            
        - CORS は JavaScript に読ませるかの制御
            
        - 本当の保護は認証・認可

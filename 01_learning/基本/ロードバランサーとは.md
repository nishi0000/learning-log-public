### 0. スレッド概要

- 扱ったテーマ：
    
    - ロードバランサー（負荷分散）の役割
        
    - DNS と「入口（固定の接続先）」の関係
        
    - サーバーが重くなる原因（CPU/メモリ/同時処理枠/DB）
        
    - Web/AP を増やしても DB がボトルネックになり得る話
        
    - DB を「分ける」代表パターン（Read Replica / シャーディング / 用途分離）
        

### 1. 扱ったトピック一覧（時系列）

-  トピック：ロードバランサーの定義と役割
    
    - 何を扱った：
        
        - LB（ロードバランサー）が「アクセス（通信）を複数サーバーへ振り分ける交通整理役」という整理
            
        - 付随機能：ヘルスチェック、入口の一本化、（構成によって）SSL終端、（構成によって）スティッキーセッション
            
        - L4/L7 のざっくり区分
            
    - 結論：
        
        - ユーザーのリクエストを複数台へ分配し、1台集中による遅延・停止リスクを下げる
            
        - 死んでいるサーバーには振らない（ヘルスチェックの前提）
            
        - L4 は主にIP/ポート（TCP/UDP）単位、L7 はHTTP内容（パス/ホスト等）を見て振り分け可能
            
    - 覚えるもの：
        
        - **LB → Load Balancer（ロードバランサー）→ 意味：負荷分散装置/役割**
            
        - **L4 → Layer 4（レイヤ4）→ 意味：トランスポート層基準の分散**
            
        - **L7 → Layer 7（レイヤ7）→ 意味：アプリ層（HTTP内容）基準の分散**
            
        - **Health Check → ヘルスチェック → 意味：生存監視して生きている先にだけ振る**
            
        - **SSL Termination → SSL終端 → 意味：HTTPS復号を入口側で担当する構成**
            
        - **Sticky Session → スティッキーセッション → 意味：同一ユーザーを同一バックエンドへ寄せる方式**
            
-  トピック：サーバー分割時に IP が変わる問題と、入口（ドメイン）の固定
    
    - 何を扱った：
        
        - 「サーバー増減でIPが変わるのでは？」に対して、`test.com` は通常 LB を向く整理
            
        - DNS は“振り分け”ではなく“名前→接続先”を返す役割、振り分けは LB が担当
            
        - 例：`test.com` → LB（入口のIP）→ 裏の複数APサーバー（プライベートIP想定）
            
    - 結論：
        
        - ユーザーから見える接続先は **`test.com`（DNS）→ LB（固定の入口）** に集約される
            
        - 裏のサーバーIPが増減/変更しても、LB配下を更新すれば `test.com` 自体は変えずに運用できる
            
    - 覚えるもの：
        
        - **DNS → Domain Name System（ドメイン ネーム システム）→ 意味：名前解決（名前→接続先）**
            
        - 「DNS=振り分け」ではない／「LB=振り分け」
            
-  トピック：アクセス集中で「サーバーが重い」の正体
    
    - 何を扱った：
        
        - リクエスト処理が同時多発し、資源上限に達して待ち行列/タイムアウトが起きる整理
            
        - 詰まりポイント：CPU、メモリ、同時処理枠（スレッド/ワーカー）、DB/外部API
            
    - 結論：
        
        - “リクエストが多い”＝“同時に処理すべき仕事が増える”→ どこかの資源が先に上限 → 待ちが増えて遅くなる/落ちる
            
        - DB/外部待ちが発生すると、待ちでスレッドが塞がり連鎖的に詰まることがある
            
    - 覚えるもの：
        
        - ボトルネック候補の最小セット：**CPU / メモリ / 同時処理枠（スレッド等） / DB・外部I/O**
            
-  トピック：Web/AP を増やしても DB がボトルネックになり得る
    
    - 何を扱った：
        
        - 入口（LB）→ Web/AP複数台 → DB基本1台、という典型構造
            
        - Web/AP を増やすと DB 問い合わせが増えて、DB詰まりで全体が遅くなる/悪化もあり得る
            
    - 結論：
        
        - LB で解決しやすいのは **Web/AP層の処理能力（CPU/スレッド/メモリ）**
            
        - DB がボトルネックの場合は、Web/AP増強だけでは改善しない（むしろDB負荷増で悪化の可能性）
            
    - 覚えるもの：
        
        - 「スケールアウト（Web/AP台数増）」と「DBボトルネック」は別問題
            
-  トピック：DB サーバーを「分ける」方法の代表パターン
    
    - 何を扱った：
        
        - 読み取りと書き込みの分離（Primary + Read Replica）
            
        - データ分割（シャーディング）
            
        - 用途分離（トランザクションDB vs ログ/検索/集計など）
            
        - 選び方の目安：参照が多い/更新が多い/ログや帳票が重い、で現実解が変わる
            
    - 結論：
        
        - **Read Replica**：参照負荷分散に効きやすいが、追随遅延（書いた直後に読めない可能性）がある
            
        - **シャーディング**：参照/更新含め分散できるが、アプリ側判断や横断集計・運用が難化
            
        - **用途分離**：重い処理（ログ/検索/集計/帳票等）を隔離してメインDB負荷を下げる方向
            
    - 覚えるもの：
        
        - **Primary → プライマリ → 意味：書き込み元（更新の正）**
            
        - **Replica → レプリカ → 意味：複製（主に読み取り先として使う）**
            
        - **Read Replica → リードレプリカ → 意味：読み取り用複製DB**
            
        - **Sharding → シャーディング → 意味：データ分割して複数DBへ配置**
            
        - **Connection Pool → コネクションプール → 意味：DB接続の再利用枠（枯渇で詰まる）**
            
        - 「参照中心→Read Replica」「更新中心→設計/ロック/分割等」「ログ/検索/帳票→用途分離」(このスレッドでの判断軸)

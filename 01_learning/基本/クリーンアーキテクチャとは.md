### 0. スレッド概要

- 扱ったテーマ：
    
    - クリーンアーキテクチャ（Clean Architecture）の概要／考え方
        
    - 依存関係の向き（外→内）と層分離
        
    - 層（Entities / Use Cases / Interface Adapters / Frameworks & Drivers）の役割
        
    - Repository を interface として内側に置き、実装を外側に置く考え方
        
    - メリット／デメリット（変更耐性、テスト容易性、コード増加など）
        

---

### 1. 扱ったトピック一覧（時系列）

-  トピック：クリーンアーキテクチャとは何か（用語の意味）
    
    - 何を扱った：
        
        - 「クリーンアーキテクチャってなんですか？」という質問への定義整理
            
    - 結論：
        
        - 変更に強くするために、依存関係の向きを統一して分離する設計
            
        - 内側＝業務ルール、外側＝手段（DB/HTTP/UI/フレームワーク）
            
        - 依存は必ず「外側 → 内側」
            
    - 覚えるもの：
        
        - 「依存は外→内」
            
        - 「内側がルール、外側が手段」
            
-  トピック：解決したい課題（設計の目的）
    
    - 何を扱った：
        
        - DB/フレームワーク変更で業務ロジックが巻き込まれる問題
            
        - テストしづらい問題（Web/DBが必要）
            
        - 入出力都合が業務ロジックに混ざる問題
            
    - 結論：
        
        - 外部要因から業務ロジックを切り離し、影響範囲を局所化する狙い
            
    - 覚えるもの：
        
        - 「変更影響を業務ロジックへ波及させない」
            
        - 「テスト容易性を上げる」
            
-  トピック：層構造（代表的な4層）
    
    - 何を扱った：
        
        - Entities / Use Cases / Interface Adapters / Frameworks & Drivers の役割整理
            
    - 結論：
        
        - Entities：業務の中心概念（ドメイン）、フレームワーク非依存
            
        - Use Cases：アプリの手順（何をするかの中心）、外部へはインターフェース越し
            
        - Interface Adapters：入出力変換（Controller/Presenter/DTO/Mapper）
            
        - Frameworks & Drivers：ASP.NET/DB/ORM/AWS/UI 等の外部“手段”の層
            
    - 覚えるもの：
        
        - 4層の名称と役割の対応
            
            - Entities＝業務概念
                
            - Use Cases＝手順（アプリの中心）
                
            - Adapters＝変換
                
            - Frameworks＝外部手段
                
-  トピック：Repository の置き方（interface を内側へ）
    
    - 何を扱った：
        
        - 「ログを保存する」などの永続化処理の扱い方
            
        - UseCase が DB を直接知らないようにする例
            
    - 結論：
        
        - 内側（UseCase）に interface（例：`ILogRepository`）を置く
            
        - 外側（DB層）で実装（例：`LogRepository : ILogRepository`）を置く
            
        - DB入れ替え時も UseCase 側の変更を最小化する狙い
            
    - 覚えるもの：
        
        - 「Repository interface は内側、実装は外側」
            
        - 「UseCase は DB を直接参照しない」
            
-  トピック：メリット／デメリット（採用時のトレードオフ）
    
    - 何を扱った：
        
        - 採用すると何が良くなり、何が増えるか
            
    - 結論：
        
        - メリット：変更に強い／単体テストしやすい／業務ルールが読みやすい
            
        - デメリット：層が増えてコード量・ファイル数が増える／小規模だとやりすぎになり得る
            
    - 覚えるもの：
        
        - メリット3点：変更耐性／テスト容易性／可読性
            
        - デメリット：実装コスト増（層・DTO・Mapper等）

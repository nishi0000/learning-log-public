### 0. スレッド概要

- 扱ったテーマ：
    
    - 設計規則における「DBテーブルのID露出禁止」の意味
        
    - 内部IDと外部公開用の識別子の使い分け
        
    - ナチュラルキーの位置づけ
        
    - 「復号ナチュラルキー」の読み取り
        
    - ルール文の平易化
        

### 1. 扱ったトピック一覧（時系列）

-  トピック：設計規則の文言の意味確認
    
    - 何を扱った：
        
        - 次の設計規則の意味を確認した  
            「データベースの各テーブルにおけるIDについては、原則として外部システム、又は表示系への露出を禁止します  
            ただし、カラムが復号ナチュラルキーとなり得る組み合わせがない場合のみ、外部システム、又は表示系への露出を許可します」
            
    - 結論：
        
        - ルール全体の意味は次の通りと整理した
            
            - DB内部で使うIDは、原則として画面や外部システムに出さない
                
            - ただし、そのデータを業務的に識別できる別の項目がない場合のみ、内部IDの露出を許可する
                
        - 一言でいうと
            
            - 内部用のIDは見せない
                
            - 見せるなら業務上意味のある番号を使う
                
            - それすらないときだけ内部IDを見せてよい
                
    - 覚えるもの：
        
        - 原則：内部IDは外部露出禁止
            
        - 例外：代わりになる識別子がない場合のみ露出可
            
-  トピック：IDの意味の整理
    
    - 何を扱った：
        
        - ここでいう「ID」が何を指すかを整理した
            
    - 結論：
        
        - IDは主に以下のようなDB内部管理用の識別子として扱った
            
            - `user_id`
                
            - `order_id`
                
            - `customer_id`
                
            - `seq_no`
                
            - 自動採番の連番
                
            - UUID などの内部管理用キー
                
        - これらはDB内部都合の値であり、外部公開向きではないと整理した
            
    - 覚えるもの：
        
        - ID ＝ DB内部管理用の識別子として扱う
            
-  トピック：外部システム・表示系への露出の意味
    
    - 何を扱った：
        
        - 「外部システム」「表示系」に何が含まれるかを整理した
            
    - 結論：
        
        - 外部システムへの露出
            
            - API連携先
                
            - CSV出力先
                
            - 他システムへの受け渡し
                
        - 表示系への露出
            
            - 画面表示
                
            - 一覧画面
                
            - URLパラメータ
                
            - 帳票
                
    - 覚えるもの：
        
        - 露出先の具体例をセットで覚える
            
-  トピック：なぜ内部IDを出さないのか
    
    - 何を扱った：
        
        - 内部ID露出禁止の理由を整理した
            
    - 結論：
        
        - 理由として次を挙げた
            
            - 内部実装に依存させたくない
                
            - 外から見ても意味がない値だから
                
            - 余計な情報漏れを防ぐため
                
        - 特に、連番IDは件数推測や内部構造の推測につながりやすいと整理した
            
    - 覚えるもの：
        
        - 理由3点
            
            - 設計変更しづらくなる
                
            - 業務的な意味がない
                
            - 情報漏れにつながる
                
-  トピック：ナチュラルキーの整理
    
    - 何を扱った：
        
        - 「ナチュラルキー」の意味を、このスレッド内の説明範囲で整理した
            
    - 結論：
        
        - ナチュラルキー ＝ 業務上もともと意味を持ち、そのレコードを一意に識別できる項目
            
        - 例として扱ったもの
            
            - 社員番号
                
            - 注文番号
                
            - 商品コード
                
            - 銀行コード + 支店コード + 口座番号
                
        - 平易化した表現
            
            - 業務的に意味のある識別子
                
    - 覚えるもの：
        
        - ナチュラルキー ＝ 業務上意味のある識別子
            
        - 例：社員番号、注文番号、商品コード
            
-  トピック：「組み合わせで一意」の考え方
    
    - 何を扱った：
        
        - 1カラムではなく複数カラムの組み合わせで一意になるケースを整理した
            
    - 結論：
        
        - 複数項目の組み合わせで一意にできるなら、その組み合わせを外部向け識別子に使うという整理をした
            
        - 例として扱ったもの
            
            - `会社コード + 社員番号`
                
            - `受注日 + 店舗コード + 伝票番号`
                
            - `テナントID + ユーザーコード`
                
    - 覚えるもの：
        
        - 1項目で足りなくても、組み合わせで識別できるなら内部IDは出さない
            
-  トピック：「復号ナチュラルキー」の読み取り
    
    - 何を扱った：
        
        - 「復号ナチュラルキー」という表現の意味を読み取った
            
    - 結論：
        
        - 文脈上は「復号」ではなく「複合ナチュラルキー」の可能性が高いと整理した
            
        - この読み方だと文意が自然になるとした
            
    - 覚えるもの：
        
        - 「復号ナチュラルキー」は「複合ナチュラルキー」の誤記の可能性が高い、という読み方
            
-  トピック：具体例での整理
    
    - 何を扱った：
        
        - 社員テーブル、商品テーブル、履歴テーブルの例で、何を外に出すべきか整理した
            
    - 結論：
        
        - 社員テーブル例
            
            - `id = 123`
                
            - `employee_code = E00045`
                
            - 外に出すのは `employee_code`
                
            - `id` は内部用
                
        - 商品テーブル例
            
            - `id = 987`
                
            - `product_code = A-001`
                
            - 外に出すのは `product_code`
                
        - 履歴テーブル例
            
            - 業務上の識別子が存在しない
                
            - この場合は例外的に `id` を出してよい
                
        - 平易な再説明では次の例で整理した
            
            - 社員テーブル
                
                - ID = 123
                    
                - 社員番号 = A001
                    
                - 名前 = 田中
                    
                - 外に出すのは `123` ではなく `A001`
                    
            - 履歴テーブル
                
                - ID = 555
                    
                - メッセージ = エラー
                    
                - 登録日時 = 2026/03/19 10:00
                    
                - 他に識別子がなければ `555` を出してよい
                    
    - 覚えるもの：
        
        - 社員番号・商品コードのような意味のある番号があればそれを出す
            
        - 履歴のように他の識別子がなければ内部IDを使う
            
-  トピック：ダメなケース／OKなケースの整理
    
    - 何を扱った：
        
        - このルールの適用例を整理した
            
    - 結論：
        
        - ダメなケース
            
            - 社員番号があるのに `id` をAPIで返す
                
            - 注文番号があるのに画面URLが内部IDだけ
                
            - 商品コードがあるのにCSVに内部IDを出す
                
            - 画面に「顧客ID: 123」のように内部IDをそのまま表示する
                
        - OKなケース
            
            - 社員番号・注文番号・商品コードのような意味のある番号を使う
                
            - 他に識別子がない場合のみ内部IDを使う
                
    - 覚えるもの：
        
        - 業務上の番号があるならそれを使う
            
        - 内部IDは最後の手段

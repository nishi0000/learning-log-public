# 実装ログ（事実ログ）— AWS × C#（.NET 8）× Vue：`POST /logs`（Supabase INSERT）導入・async/await・レスポンス共通化（秘匿情報マスク版）

更新日時: 2026-01-18 +0900（会話日時ベース）

## 1. 作業目的

- `POST /logs` で受け取った JSON を Lambda で `LogsRequest` DTO に Deserialize できることを確認
    
- `POST /logs` の受け取り結果をレスポンスに含めて返し、入力到達を確定
    
- `/logs` を Supabase（PostgreSQL / 外部DB）へ INSERT し、DB永続化できることを確認
    
- 400/404/500 のレスポンスを共通化し、JSONで返す
    

---

## 2. 作業対象（環境）

- API: API Gateway（HTTP API） + AWS Lambda（C# / .NET 8）
    
- Lambda 入力: `APIGatewayHttpApiV2ProxyRequest`
    
- Lambda 出力: `APIGatewayHttpApiV2ProxyResponse`
    
- JSON: `System.Text.Json`
    
- 検証: PowerShell（`Invoke-RestMethod` / `ConvertTo-Json -Compress`）
    
- ログ確認: CloudWatch Logs
    
- DB: Supabase（PostgreSQL / Table Editor）
    

---

## 3. 実施内容と結果

### 3.1 レスポンス生成の共通化（Error関数）

**何をした**

- `Error(int statusCode, string message)` を追加し、`BadRequest/ServerError/NotFound` を集約
    
- `Body = JsonSerializer.Serialize(new { error = message })` でエラーJSONを生成
    

**何が起きた**

- 文字列連結（`"{\"error\":\"...\"}"`）を廃止し、Serializeで統一できる形になった
    

**現在どうなっている**

- 400/404/500 は `Error(...)` 経由で JSON（`{"error":"..."}`）を返す
    

---

### 3.2 `POST` ルーティング（`/logs` と `/todos`）

**何をした**

- `method == "POST"` のブロック内で `path.EndsWith("/logs")` / `path.EndsWith("/todos")` により分岐
    
- Body 空の場合は 400（`empty body`）を返す
    

**何が起きた**

- ステージ名を含むパスでも末尾一致でルーティング可能になった（例：`/prod/logs`）
    

**現在どうなっている**

- `POST` は `/logs` と `/todos` のみ処理し、それ以外は 404 を返す
    

---

### 3.3 `POST /logs` の DTO Deserialize と Supabase INSERT へ方針変更

**何をした**

- `public record LogsRequest(DateTime ts, string type, string text);` を使用
    
- `JsonSerializer.Deserialize<LogsRequest>(body)` で DTO 化
    
- `payload = new { dto.ts, dto.type, dto.text }` を作成し JSON 化
    
- Supabase の Data API（PostgREST）に HTTP POST する実装を追加
    

**何が起きた**

- `POST /logs` の処理が「echo返却」から「SupabaseへINSERTして、返りを返す」へ移行した
    

**現在どうなっている**

- `POST /logs` は DTO Deserialize 後、SupabaseへINSERTし、Supabase返却JSON（id含む）をレスポンスに使う
    

---

### 3.4 環境変数の導入（Supabase URL/Key）

**何をした**

- `Environment.GetEnvironmentVariable("SUPABASE_URL")`
    
- `Environment.GetEnvironmentVariable("SUPABASE_ANON_KEY")`
    
- CloudWatch Logs に存在確認ログを出力
    

**何が起きた**

- CloudWatch Logs 上で `SUPABASE_URL exists = True` / `SUPABASE_ANON_KEY exists = True` を確認できた
    

**現在どうなっている**

- Supabase接続情報はコードに直書きせず、Lambda環境変数から取得する構成
    

---

### 3.5 `async/await` の導入（Supabase HTTP 呼び出し）

**何をした**

- `FunctionHandler` の戻り値を `async Task<APIGatewayHttpApiV2ProxyResponse>` に変更
    
- `HttpClient.SendAsync` / `ReadAsStringAsync` を `await` で実行する構造に変更
    
- `using var` を利用して `HttpClient` / `HttpRequestMessage` をスコープ終了時に破棄
    

**何が起きた**

- 署名変更の初期試行で `Task` を引数側に置く誤りが発生したが、戻り値側へ修正して確定した
    
- `return` 抜け（`BadRequest(...)` / `ServerError()`）が残っていた箇所を `return` 付きに修正し、分岐が確定した
    

**現在どうなっている**

- `POST /logs` 内で Supabase への HTTP 呼び出しを `await` で実行する（I/O待ちを含むため非同期）
    

---

### 3.6 Supabase（Table Editor）で `logs` テーブル作成

**何をした**

- Supabase ダッシュボードで `public.logs` テーブルを作成
    
- 列（画面表示から確認できる範囲）
    
    - `id (int8)`
        
    - `ts (timestamptz)`
        
    - `type (text)`
        
    - `text (text)`
        
    - `created_at (timestamptz)`
        

**何が起きた**

- Table Editor で “This table is empty” 表示を確認（データ未投入状態）
    

**現在どうなっている**

- `public.logs` テーブルが存在し、INSERT可能な状態
    

---

### 3.7 Supabase INSERT 成功（PowerShell + Table Editor 確認）

**何をした**

- PowerShell `Invoke-RestMethod -Method Post -Uri $uri -ContentType "application/json" -Body $body` で `POST /logs` を実行
    
- レスポンス内容を確認
    
- Supabase Table Editor で行が追加されたことを確認
    

**何が起きた**

- レスポンスに `id`, `ts`, `type`, `text`, `created_at` が含まれて返却された
    
- Supabase `public.logs` に同内容の行が追加された（`id=1` が付与）
    

**現在どうなっている**

- `POST /logs` → Lambda → Supabase INSERT → Supabase返却（id付与）→ クライアント返却 まで疎通できている

## 4. 変更したコード要素（抜粋：構造）

- `FunctionHandler`: `async Task<APIGatewayHttpApiV2ProxyResponse>` に変更
    
- `LogsRequest` DTO を利用して `POST /logs` の body を Deserialize
    
- Supabase PostgREST のエンドポイントを組み立て
    
    - `{SUPABASE_URL}/rest/v1/logs`
        
- SupabaseへのPOST時に付与したヘッダー（実装ベース）
    
    - `apikey: {SUPABASE_ANON_KEY}`
        
    - `Authorization: Bearer {SUPABASE_ANON_KEY}`
        
    - `Prefer: return=representation`
        
    - `Content-Type: application/json`（`StringContent` で指定）
        
- エラー応答の共通化
    
    - `Error(statusCode, message)` → `BadRequest/ServerError/NotFound`

## 6. 最終状態（確定）

- Lambda は `APIGatewayHttpApiV2ProxyRequest/Response`（HTTP API v2）で統一
    
- `POST` は `path.EndsWith("/logs")` と `path.EndsWith("/todos")` で分岐
    
- `POST /logs` は
    
    - Body 空 → 400 `{"error":"empty body"}`
        
    - JSON不正 → 400 `{"error":"invalid json"}`
        
    - Supabase設定不足（環境変数未設定想定）→ 500 `{"error":"internal error"}`
        
    - 正常 → SupabaseへINSERTし、返却されたJSON（id/created_at含む）を 200 で返す
        
- Supabase は `public.logs` テーブル作成済みで、`POST /logs` によりレコードが追加されることを確認済み
    
- エラー応答は `Error(...)` 経由で Serialize して返す構造に共通化済み
